# 技术文档与真实开发流程说明

2026-11-05。面向第一次推进真实软件开发的项目负责人。本文主体保留阶段 6 交付时的流程说明；其中“本次只交付文档”“未提交/未测试”是历史状态。随后用户已授权阶段 7 开发，当前实现与真实验收见 [实施记录](../../development/book-c-2026-11-05/IMPLEMENTATION.md)。技术入口：[技术框架](../../technology/book-c-2026-11-05/FRAMEWORK.md)、[技术设计](TECHNICAL.md)、[独立测试交接](TEST-HANDOFF.md)。

## 1. 技术文档是做什么的

PRD 解释“为谁解决什么问题、应该有什么行为、怎样验收”；设计稿解释“页面如何呈现、用户怎样操作”；技术文档把这些变成“代码分成哪些模块、数据如何保存、异常怎么处理、怎样验证和交付”。

例如“结束后清空条件”是一条产品要求。技术设计需要继续回答：什么时候才算结束成功？先写记录还是先清会话？保存失败还能重试吗？点两次会不会记两条？这些决定无法仅靠页面截图表达。

技术文档让开发者、测试者和未来接手的人按照同一套规则工作，也让你能审查“为什么这样实现”。它无需把每行代码翻译成中文；应记录难以从代码看出的约束、理由、接口和失败处理。

## 2. 本项目技术文档必须包含什么

| 内容 | 要回答的问题 | 本次位置 |
| --- | --- | --- |
| 范围与依据 | 做什么、不扩大到哪里、对应哪版 PRD/设计 | TECHNICAL 1 |
| 技术选型 | 为什么选它、其他方案代价、版本与风险 | FRAMEWORK |
| 架构和模块 | 哪段代码负责什么、如何调用 | TECHNICAL 2 |
| 数据和接口 | 字段、ID、单位、生命周期、输入输出 | TECHNICAL 3 |
| 核心算法与状态 | 推荐、分页、计时、完成和恢复如何工作 | TECHNICAL 4–5 |
| 异常与数据安全 | 损坏、存储失败、导入、升级、回滚怎么处理 | TECHNICAL 6 |
| 界面工程约束 | 字体素材、适配、三语言、主题、键盘 | TECHNICAL 7 |
| 开发和构建 | 环境、依赖、命令、产物、平台桥 | TECHNICAL 8 |
| 测试和验收 | 测哪些风险、谁验收、证据在哪里 | TECHNICAL 9、TEST-HANDOFF |
| 交付和演进 | 开发切片、Git 合并、待决项和文档更新 | TECHNICAL 10–11 |

这是适合本项目的最小实用集合，不是所有公司通用的固定格式。没有后端就不编造服务器 API 文档，没有同步需求就不写一套云架构。

## 3. 技术文档是否一直使用同一个

**保留一套清楚的当前基线，开发中持续更新。** 当前 TECHNICAL.md 是主入口；框架选择、独立测试分开存放并互相链接。不要每次新增“最终版2”“最终版3”却保留多份相互矛盾的现行规则。

小变动直接更新对应章节，与代码一起提交。大决定（例如换框架、换数据库、改变记录时间口径）增加 ADR，记下背景、备选、选择原因、兼容风险与验证办法。主文档链接新决定，旧决定保留为历史。发布 tag 固定当时文档与代码，之后仍可继续更新。

文档描述“目标契约”和“当前实现”时要明确区分：本次是实现方案，新增构建命令和模块尚未落地；未来实现完成后，补对应提交与真实运行结果。

## 4. PRD 和设计稿后续会不会修改

**会。** 真实使用反馈、实现中的限制、可访问性问题、边界数据和测试发现，都可能要求修改。已经开始开发也不等于需求冻结到永远；但不能随口改完后只让代码知道，其他资料继续写旧规则。

一个合适的变更流程是：记录问题和影响 → 判断是 bug 还是需求改变 → 更新对应 PRD 验收与设计 → 评估技术/数据兼容代价 → 改代码和测试 → 独立验收 → 合并。纯技术内部重构可不改 PRD；按钮布局改变要同步设计，业务行为改变要先同步 PRD/交互契约。

2026-11-06 用户补充：界面或交互确定最终版本后，再新建独立 worktree 和 GPT 窗口，同步对应 Figma 页面或组件。交接固定已验收提交、变化清单和目标节点；核对 Figma 账户 `3966592487` 后执行，记录更新后的节点链接与截图。迭代中先更新文字契约，不把尚未验收的中间版本同步为最终设计。

例如把 C 日历从“今天记录”改为“月历排期”就是新增需求，应先说明价值与范围；修复“第 11 项任务看不到”则是实现已有分页要求的 bug，不需要重新定义产品方向。

## 5. 要等所有 PRD 和设计最终完成才 coding 吗

通常按可验收的小切片推进。先让整体目标、数据边界、主流程和高风险规则足够明确，再把**本次切片**的需求、设计、技术方案和验收条件明确到可开发，随后实现、测试、收集反馈。后续切片继续细化。

对于本项目，可以先做工程化和数据保护，再做首页、任务增删改、计时和日历等切片；每片都能演示并验证。不要等所有未来功能都有“最终设计”才动工，也不要在计时和数据保存规则尚不明确时边猜边写。

| 工作类型 | 是否需要先补 PRD/设计 |
| --- | --- |
| 抽取现有推荐函数、保留行为 | 通常无需改 PRD，技术文档与回归测试同步 |
| 实现已确定的 C 任务分页 | 当前验收已明确，复核相应 Figma 节点后即可按切片开发 |
| 增加窄屏单页旧书布局 | 需要补适配设计与验收规则，不能擅自作为批准方案 |
| 增加账号同步、修改“完成”含义 | 先做需求决定，再设计、技术评估和实现 |

参与者测试用于判断“人是否理解、愿不愿意使用”；代码测试用于判断“是否按规则工作”。两者不能互相代替。原型测试未完成可以保留为明确待办，不等于产品效果已经证明。

## 6. 你的 Git 仓库怎么处理

当前无需另建仓库。本地历史可衔接：master 是 design/minimal-ui 的祖先，后者领先 10 个提交。未提交改动与未跟踪文档较多，属于需要整理的工作区状态，没有证据说明 Git 历史不可用。远端引用还需在实际合并前 fetch 复核。

先审查并保存现有用户改动，再分小提交开发；design/minimal-ui 作为集成线，最后合入 master。新建仓库会割断现有版本、问题和发布的关联，也不能自动解决文档与代码没有及时提交的问题。本次没有替你提交、切分支、合并或发布。

代码完成后，按你的要求另开一个 GPT 窗口独立测试，固定待验收提交并使用独立 worktree/profile；开发窗口自测仍要先做。独立测试报告列出通过、失败和未测项，修复后复测，最后才合入 master。新开浏览器窗口本身不等于独立 GPT 验收。

本次只交付选型和技术文档，没有新增产品代码，所以还未触发“写好代码后另开窗口测试”。交接模板已准备好，不把当前 128 项旧测试通过冒充未来独立验收。
