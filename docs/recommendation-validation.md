# 推荐筛选与状态验证

日期：2026-10-20。基线：`5ffbaef`，分支 `master`，开始时工作区干净。仅处理推荐及直接相关状态，不实现分页、悬浮窗、日记或统计，不迁移技术栈。

本记录保留上一轮的实现与测试结果；后续用户反馈、避免连续重复推荐及可重复任务语义调整，见 [本轮反馈验收记录](recommendation-feedback-validation.md)。其中连续重复策略已按新要求更新，以下描述是上一轮的历史口径。

## 实际问题

基线 `app.js` 的 `ok(t)` 已使用 `t.minutes <= time`，不存在“仅匹配相同时长”的比较表达式。不能把本轮描述的现象归因于相等判断。小于和等于边界在修复前测试中均通过。

`minutes` 是数值：任务表单使用一元 `+` 转换，导入校验要求 `Number.isFinite(t.minutes)` 且范围为 1–1440；可用时间按钮值也转为数字。环境、电脑、启用状态及目标有效性是附加硬条件，短任务仍可能因为这些条件被排除。

实际复现的缺陷是时间、环境和电脑偏好修改后只保存偏好，没有刷新推荐卡片；推荐开始按钮也没有重新校验条件，并引用共享的 `cur`，可能使用过期推荐。首批 16 项 Node 测试中 10 项通过、6 项失败，失败集中于这些状态路径。

## 最小修复

- `persistPreferences()`：只有偏好成功保存后才重新调用 `random()`；保存失败仍返回失败并沿用已有回退机制，不显示与原偏好冲突的新卡片。
- `startRecommendation(id)`：使用卡片创建时捕获的任务 ID 查找当前任务，检查其仍是当前推荐并满足 `ok(t)`；不满足时只重新推荐，不开始任务。
- `random()`：保留候选筛选、近 7 天避重、随机抽取、换一个和空状态；仅将开始按钮改为调用新的推荐入口。

`ok()` 的时间上限及其他硬条件保持原实现。没有修改 `run()`、`startTimer()`、`finishTimer()`、历史记录写入、任务库筛选、数据格式、迁移或 HTML 安全渲染。

## 筛选顺序

1. 任务启用、预计时长 ≤ 可用时长、所属目标有效或为空。
2. 需要电脑的任务必须满足当前电脑可用偏好。
3. 任务环境与当前环境精确一致；听课环境额外排除需要电脑的任务。
4. 从上述候选中优先避开近 7 天完成的任务；若全部候选都近期完成，仅回退到同一硬条件候选集，不扩大时间或环境范围。
5. 随机选择；无候选时使用现有空状态，允许前往任务库。

手动从任务库选择任务沿用原行为，不被开始页推荐条件拦截。重复抽取仍可能得到同一个符合条件的任务，不引入新的随机权重或“换一个必不同”规则。

## 状态与历史记录

完成任务原本已经清空 `cur` 和推荐卡片，跳转今天页；返回开始页重新调用 `random()`。本轮验证这一流程，没有改动计时器完成逻辑。

有其他未近期完成的候选时，完成后返回会优先选其他任务；若只有一个满足硬条件的任务且已完成，原避重回退仍可再次推荐它，这是重新计算的结果，不是旧卡片残留。

更换推荐、刷新条件或返回页面均不调用完成记录写入。测试验证完成一次后反复刷新、返回及再次触发完成，不产生额外记录；原有完成 ID 防重复机制保持不变。
